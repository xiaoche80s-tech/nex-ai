# AgentSpec 发布门禁：发布清空草稿的显式状态机

现状 `publish()` 唯一校验是「草稿非空」，但草稿恒非空（创建必带、无清空路径），任何时刻点发布都成功——重复发布产生内容相同的无效版本。决定采用**显式状态机：发布时清空草稿**，编辑保存重建草稿，仅草稿态（有草稿）可发布；「没有可发布的草稿」从此成为真实的领域门禁，并发场景下后者发布自然报错，无需额外防重。

## Considered Options

- 变更推导（草稿与当前生效快照值判等，无变更即拒绝发布，不存状态字段）——**拒绝**：编辑后改回原样会被拒绝发布，用户反而困惑；显式状态机的「发布即回到稳定态」产品语义更直白可解释。
- 仅前端按显示状态禁用发布按钮——**拒绝**：绕过 UI 仍可发布，门禁形同虚设。
- 已发布态下显式「创建新草稿」两段式入口——**拒绝**：编辑不保存即无副作用，无需仪式负担，入口仍统一叫「编辑」。

## Consequences

- 已发布态下编辑回填来源改为当前生效快照（getSpec 语义调整）。
- 切换版本只回退当前版本指针，不动草稿——切换与写草稿是两条独立工作线，无丢稿风险。
- `ai_spec` 表 2026-08-24 已按脚本重建，无存量迁移；SQL 初始化脚本的 draft 列注释随「发布后清空」新语义同步。
